# 关于Tauri框架的选型与开发进程

### 本地搜索 + 启动器：同一个“搜索调度器”的两个出口

你要求的“悬浮 UI + Tab 切换 + 触发词路由 + 启动器”，在架构上可以收敛为**一个常驻的搜索调度器**，而不是多个独立功能拼在一起。

调度器的输入是“用户敲进悬浮框的字符串 + 当前模式（本地/网络）”，输出是“一组可执行的动作或结果”。它内部做三件事：

1. **模式判定**：Tab 键在本地/网络之间切换，这个状态由调度器持有。
    
2. **触发词路由**：如果输入以某个已注册触发词开头，剥离触发词，把剩余部分交给对应的小程序处理器。
    
3. **回退到默认搜索**：没有触发词时，本地模式走 `SearchBackend`，网络模式走 AI 搜索子代理。
    

启动器不需要单独的“面板系统”。搜索框为空时，悬浮 UI 直接展示一个静态的快捷启动网格即可；输入非空时，网格让位于结果列表。这样启动器和搜索框在 UI 上是同一个浮层在不同状态下的两种渲染，逻辑集中，交互也符合你“弃用鼠标类交互”的设定。

**预览与打开**：本地结果需要支持“打开”和“预览”。Windows 上可以用系统关联直接 `ShellExecute` 打开；预览图片可以走缩略图缓存，文档预览初期建议只做“打开所在文件夹”或“用默认程序打开”，不要过早陷入格式渲染的泥潭。Mac 端同理，用 `open` 命令分发。

### 🌐 网络搜索：不要自己拼搜索 API，做一个“AI 搜索子代理”

你对网络搜索的重构设想，**DeepSeek 在 2026 年 10 月开放的独立 Search / Fetch API 几乎是现成的答案**。两个端点分工明确：`/v1/tools/search` 按 query 返回结构化网页列表（含标题、摘要、`rerank_score` 相关性评分、`authority` 权威度），`/v1/tools/fetch` 抓取指定 URL 并以 Markdown 返回全文。定价是**每千次成功请求 $0.75（约 5 元人民币），失败、无结果、超时不计费**，约为 Tavily 的十分之一。速率限制每端点 5 QPS，对个人工具完全够用。[](https://news.qiniu.com/archives/1792373734665#1)[](https://36kr.com/p/4032549827876480#1)

但这不意味着你要在本地手搓一个完整的 RAG 管道。更合理的架构是：**你的应用维护一个“搜索子代理”，把 Search / Fetch 作为工具暴露给模型，让模型自行决定搜什么、抓什么、如何综合**。这正是 DeepSeek 自己描述的 Agent 时代标准动作——模型判断需要联网时，服务端调 Search 拿结构化结果，再用 Fetch 抓正文，干净的 Markdown 直接进上下文。你在客户端侧只需要做三件事：[](https://36kr.com/p/4032549827876480#1)

- 把用户输入包装成一次带工具定义的模型调用；
    
- 流式呈现模型生成的回答，并在回答中嵌入来源引用；
    
- 如果用户想深入某个结果，再触发一次 `fetch` 获取全文。
    

**成本控制**：按你的使用频率，假设每天 50 次搜索查询，月均约 1500 次，按 $0.75/千次计算，**月成本约 1 美元量级**。真正的变量是模型 token 消耗，如果让模型做多轮搜索+综合，单次查询的 token 量会高于纯搜索。建议初期设置一个“最多搜索 3 次、最多抓取 2 个页面”的硬上限，避免模型在开放工具下过度调用。

### 🧩 小程序框架：借鉴 Wox 的“宿主隔离”思路，而不是简单函数注册

你明确要求“保留研发框架，以后可复用扩展”。这意味着小程序不能是一堆硬编码的 `if-else` 触发词分支，而需要一个**路由 + 处理器的注册机制**。

Wox 的插件架构提供了一个直接可参考的范式：**核心进程与插件进程隔离**。Wox 的 Go 核心负责查询路由，第三方插件运行在独立的“语言宿主”进程中，通过 WebSocket JSON-RPC 通信。这样做的好处是插件崩溃不会拖垮主进程，插件也可以用不同语言编写。对于一个个人工具来说，完整的多语言宿主可能过重，但**隔离的思路值得保留**：[](https://blog.gitcode.com/c8993aa615542a339865a168e0facad8.html#1)

- **路由层**：维护一个 `TriggerRegistry`，每个条目包含触发词、匹配规则、处理器标识。调度器在输入阶段只做“匹配触发词、剥离、转发”，不关心处理器内部实现。
    
- **处理器层**：初期五个小程序（翻译、单位转换、数字转大写、二维码、计算器）全部用 Rust 写在主进程内即可，但每个处理器实现同一个 `MiniApp` trait（输入字符串 → 输出结构化结果/UI 指令）。以后要扩展到独立进程或动态加载，路由层不需要改动。
    

翻译和单位转换如果走在线 API，注意把网络调用放在处理器内部、异步执行，不要让一个慢请求阻塞整个搜索框的输入响应。计算器和数字转大写是纯本地逻辑，成本极低，可以作为最先跑通框架的“冒烟测试”小程序。

### 🧱 局域网与皮肤：留白的具体方式

**局域网 / 社交 / 文件快传**：你要求“保留框架、先留白”。在架构上，这意味着**不要把任何网络通信逻辑硬编码进搜索调度器**。可以预留一个 `PeerService` 接口（定义设备发现、消息信封、文件传输的抽象方法），但 Windows 和 macOS 的实现先留空或返回“未启用”。将来填充时，它作为一个独立的后台服务接入，不侵入搜索和小程序的路由逻辑。这样“留白”是真正的架构留白，而不是留下一堆 TODO 注释。

**皮肤系统**：明暗两套主题用 CSS 变量或 Tauri 的前端主题上下文即可实现。悬浮框的背景、文字、结果高亮色都走同一组变量，切换主题就是切换一组变量值。**不要引入皮肤文件格式或皮肤编辑器**，两套主题的维护成本几乎为零，一旦开始做皮肤系统，成本曲线会陡峭上升。

### 📋 一个建议的落地顺序

|阶段|目标|验证点|
|---|---|---|
|**第 1 步**|Tauri 悬浮框 + 全局快捷键 + 空状态启动网格|浮层能唤出、能键盘操作、能启动程序|
|**第 2 步**|`SearchBackend` 接口 + Windows 后端（UFFS 或 Everything SDK）|本地文件/文件夹/App 的毫秒级检索与打开|
|**第 3 步**|搜索调度器 + Tab 模式切换 + `TriggerRegistry` 路由|本地搜索与触发词路由在同一个输入流中不冲突|
|**第 4 步**|五个小程序处理器接入，框架跑通|触发词正确路由，慢请求不阻塞输入|
|**第 5 步**|AI 搜索子代理接入 DeepSeek Search/Fetch|网络模式能返回带引用的综合结果|
|**第 6 步**|macOS `mdfind` 后端适配|同一套调度逻辑在 Mac 上可用（搜索能力弱于 Windows 可接受）|

这个顺序里，第 3 步是整个项目成败的关键节点。**先把“一个输入、多种去向”的调度逻辑跑通，再往里面填充具体能力**，比先做一堆孤立功能再想办法缝合要省力得多。局域网和皮肤留白放在第 6 步之后，不影响主线交付。

# 关于薄桥接层的说明

### 这个建议成立的部分

AI 写 Rust 的摩擦点集中在几类：所有权转移路径、生命周期标注、`async` 块里的借用跨越 `.await`、`&mut` 与 `&` 的冲突、trait object 的 `dyn` 兼容性。这些错误的特征是**代码看起来完全合理，但编译器报错信息指向的位置和真实问题隔了好几层**，AI 自我修正的成功率低，容易陷入“改一处、错三处”的循环。

把 UI 状态（浮层显示/隐藏、Tab 模式、输入框内容、结果列表渲染、主题切换）和业务编排（触发词匹配、结果排序、快捷启动网格的数据组织）放在 TypeScript 侧，确实能绕开这类摩擦。这些逻辑本来就是事件驱动的状态机，TS 的生态和 AI 的训练数据都更厚，生成质量更稳定。

### 需要警惕的盲区：“薄”不等于“零”，更不等于“无设计”

**第一个盲区：本地搜索后端不可能“薄”。** 如果你走 UFFS 路线，查询逻辑、索引管理、结果过滤都在 Rust 侧，这是一个**有明确边界的厚模块**。正确的做法不是把它削薄，而是**把它隔离成一个对外接口极简的模块**——暴露 `search(query, limit) -> Vec<SearchResult>` 这一个 command，内部怎么用 UFFS、怎么处理索引更新，全部封在模块里。AI 不需要频繁改动这个模块，改的时候也集中在一两个文件，出错面可控。这比强行把搜索逻辑搬到 TS 侧、每次查询都 IPC 传全量结果再过滤要合理得多。

**第二个盲区：桥接层设计不好会碎片化。** “薄桥接层”最常见的失败形态是**每个操作一个 command**：`open_file`、`reveal_in_folder`、`copy_path`、`register_hotkey`、`toggle_window`……command 数量膨胀，每个都有一组参数类型要维护，Rust 和 TS 两边的类型定义容易漂移。更合理的做法是**按领域聚合 command**：一个 `search` 领域、一个 `launch` 领域、一个 `system` 领域，每个领域内部用枚举参数区分操作。这样桥接层代码量小，但接口是成体系的。

**第三个盲区：TS 侧不是没有复杂度，只是 AI 更容易绕过。** 搜索调度器如果放 TS，它要处理“输入事件 → 模式判定 → 触发词路由 → 调用 Rust command 或 TS 处理器 → 结果渲染”这条链。AI 写 TS 的坑在异步竞态（快速输入时旧请求后返回覆盖新结果）、状态管理（浮层状态和搜索结果状态的一致性）。这些坑比 Rust 的所有权问题好排查，但**不代表不需要设计**。建议调度器从一开始就用一个明确的状态机（可以用 XState，也可以手写 reducer），不要让 AI 自由发挥出一堆散落的 `if (loading) ...`。

### 对你这七个需求的具体划分建议

|模块|放哪侧|理由|
|---|---|---|
|全局快捷键、窗口显隐、系统托盘|**Rust 薄层**|纯系统 API 调用，无业务逻辑，正是薄桥接层的典型场景|
|本地搜索后端（UFFS/mdfind 封装）|**Rust 厚模块，接口极简**|性能敏感、依赖系统能力，必须留 Rust，但对外只暴露 `search` 一个 command|
|打开文件/文件夹/App、预览|**Rust 薄层**|`ShellExecute` / `open` 一行调用，TS 侧只传路径和动作枚举|
|搜索调度器（Tab 切换、触发词路由）|**TS**|纯状态机逻辑，AI 生成 TS 的成功率高；它决定“调哪个 command”，不碰系统调用|
|启动器网格、结果列表、主题|**TS**|纯 UI 状态，放 Rust 侧纯属自找麻烦|
|五个小程序处理器|**TS 优先**|计算器、单位转换、数字转大写、二维码、翻译都是纯逻辑或 HTTP 调用，TS 生态成熟；小程序注册表也放 TS|
|AI 搜索子代理（调 DeepSeek Search/Fetch、流式渲染）|**TS 为主，Key 存储走 Rust**|fetch/SSE 在前端生态更顺；API Key 存系统钥匙串需要 Rust command|
|局域网/社交框架留白|**Rust 侧定义 trait，TS 侧定义事件契约**|先留接口，不实现；将来填充时作为独立后台服务接入|

### 一个能显著降低维护成本的增强

既然桥接层是 Rust 和 TS 的接缝，**用 `tauri-specta` 或类似工具从 Rust command 自动生成 TS 类型**。这样 Rust 侧改一个参数类型，TS 侧编译时就能发现不匹配，而不是等到运行时 IPC 反序列化失败。这把“薄桥接层”从“两份手工维护的类型定义”变成“一份定义、两边同步”，是对原建议的实质增强。

### 最终判断

**采纳这个建议，但要修正它的表述**：不是“把 Rust 限制在薄桥接层”，而是**“把 Rust 的厚度集中在少数几个接口极简的系统能力模块里，其余全部放 TS”**。具体到你的项目，Rust 侧只需要三个有明确边界的部分——系统集成薄层、搜索后端厚模块（接口薄）、安全存储薄层——其余调度、路由、小程序、UI 全部放 TS。这样既避开了 AI 写 Rust 的高频翻车区，又不会因为强行削薄而把性能敏感逻辑推过 IPC 边界。
